# AR-0002: Correctness-first coordinator upgrade protocol

## Objective

Define and implement a release upgrade path for the coordinator that preserves a
functional, usable coordination system at every externally observable point,
including interruption and failure paths.

## Non-negotiable invariants

- No upgrade mutates authoritative state until all prerequisites pass and a
  complete, restorable backup is verified.
- Workers, leases, wrapped commands, reconciliation, and publication are
  quiesced before replacement; active work is never silently discarded.
- Every intermediate state is either the verified old runtime or the verified
  new runtime. Partial vendor, binding, backend, or projection states fail
  closed and are recoverable.
- A failed upgrade restores the last known-good coordinator runtime and proves
  task, revision, lease, binding, backend, and projection integrity before
  reopening work.
- Retry and recovery are idempotent and never repeat an ambiguous external
  command.
- Product worktrees and unrelated task history are not rolled back.

## Acceptance

- A stable, versioned, machine-readable release-upgrade contract is generated
  for every release and checked into the release evidence.
- `handoffctl upgrade check|plan|apply|rollback` has explicit approval and
  fail-closed behavior.
- Git and SQLite backends have complete backup, restore, crash, and equivalence
  coverage.
- TLA+ models cover upgrade phases, quiescence, backup-before-replacement,
  atomic commit, crash recovery, rollback, and reopening only after validation.
- Fault-injection, multiprocess, interrupted-process, corrupted-release,
  failed-push, and repeated-retry tests pass.
- A first released upgrade is independently reviewed, exact-head CI-green,
  freshly cloned, and rollback-tested before being advertised.

## Dependency order

Complete AR-0003 through AR-0006 before implementation of AR-0007. AR-0008
must validate the combined protocol before AR-0009 and AR-0010 publish it.
