# AR-0007: Upgrade engine and rollback

Implement the explicit `upgrade check`, `upgrade plan`, `upgrade apply`, and
`upgrade rollback` flow. Use the repository-common lock, durable phase records,
bounded commands, atomic replacement, exact revisions, and idempotent resume.

The engine must distinguish preflight failure, staged-but-not-committed
failure, post-upgrade failure, rollback failure, and ambiguous external
results. It must never claim success while the runtime, binding, backend,
projections, or backup state is uncertain.

## BackupBoundary v2 normative design (2026-09-14)

This section is a design gate, not an implementation claim. No adapter may be
published until an independent reviewer accepts this contract and its hostile
tests.

### Envelope and path domain

Every operation carries a strict serialized envelope with exactly these
fields: `schema_version=2`, `backend` (`git` or `sqlite`), `project_id`,
`operation_id`, positive `state_revision`, `authority_revision`,
`fencing_token`, `fencing_owner`, `durable_barrier_id`, `artifact_root`,
`source`, `destination`, `manifest`, and `quiescence_record_digest`.
Identity strings use `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; UUID/project values
are validated by their existing project contract. Public evidence exposes
only opaque artifact IDs and digests, never host paths.

`artifact_root` is an existing, non-symlink directory owned by the authority.
Only generated outputs (`destination`, `manifest`, and operation sidecars)
must be beneath its resolved inode; the live source may be the configured
Git/SQLite authority outside that root. Source and every output must be
existing/typed as required by the backend or a non-existing output target,
respectively; no source/output or output/output ancestor/descendant overlap is
allowed. All lexical ancestors and leaves reject symlinks, and resolved inode
identity rejects hard-link aliases. Existing outputs are never overwritten.

### Authoritative barrier and lock sequence

The engine obtains the repository-common `handoffctl.coordinator_lock_path()`
lock first; callers cannot select a substitute. Under that lock it acquires
the authoritative durable barrier using compare-and-swap on
`durable_barrier_id`, records owner/token/state revision, and fsyncs the
barrier record and containing directory. It then re-reads the barrier,
authority revision, project binding, backend selector, and fencing token
immediately before backup and immediately after verification. The barrier is
held through backup, isolated restore-equivalence verification, manifest
publication, and post-check; release is a durable reopen operation after the
engine records success. Any mismatch, stale owner, lost barrier, or failed
re-read fails closed.

### Durable operation/retry state

The operation journal stores the canonical envelope digest, output artifact
digests, phase, and outcome. A retry with absent outputs is allowed only for
the same operation ID and exact envelope when no terminal artifact record was
published; a terminal verified record is idempotently returned without
rewriting outputs. Any partial output, digest mismatch, changed path, stale
revision, or ambiguous external result enters reconciliation/safe mode and
cannot be blindly retried. Recovery must distinguish `started`, `published`,
`verified`, and `ambiguous` records.

### Backend API and durability contract

Adapters use bounded public APIs. Git backup/restore must use bounded commands
with explicit timeout, complete refs/object/index/worktree evidence, and
restore into an operation-unique isolated destination followed by commit,
ref, tree, and binding equivalence checks. SQLite must obtain binding and
authority revision from the live store, use the online backup API, persist a
canonical sidecar manifest, and restore with integrity, WAL, binding, and
projection equivalence checks; caller booleans and supplied binding alone are
not evidence. Every artifact file is written, flushed, fsynced, atomically
renamed, and followed by directory fsync in that order. Rename, fsync,
cleanup, timeout, process death, and directory failure at each boundary
produce an explicit failed/ambiguous outcome; no success is reported after an
uncertain durability point.

### Required review evidence

Before implementation approval, tests must cover source outside root,
ancestor overlap, symlink and hard-link aliases, malformed identities and
stale authority/barrier/fence revisions, common-lock contention and ordering,
same-operation retry/recovery, concurrent different operations, every write/
rename/fsync/cleanup/timeout fault, process death at each durable boundary,
Git/SQLite restore equivalence, and privacy-safe evidence. The design remains
blocked until these predicates are independently reviewed and mapped to the
formal model.

## BackupBoundary v4 corrections (2026-09-14)

The v3 design is rejected for a circular digest dependency and an ambiguous
Git-mode barrier store. These corrections are normative and supersede the
conflicting v3 clauses.

### Non-circular barrier identity

`quiescence_record_digest` is removed. The envelope instead contains
`barrier_identity_digest`, calculated once as SHA-256 over canonical JSON of
only the immutable identity tuple:
`{schema_version, project_id, operation_id, state_revision,
authority_revision, durable_barrier_id, fencing_token, fencing_owner}`.
The tuple excludes `envelope_digest`, barrier status, timestamps, and all
mutable outcome fields. The envelope digest is then calculated over the full
canonical envelope including `barrier_identity_digest`. The barrier record may
store the envelope digest, but its CAS-mutated status/timestamps can never
alter the barrier identity digest. Any mismatch is a fail-closed identity
failure, not a retry signal.

### Concrete Git-mode barrier store

When the coordination state backend is Git, the barrier is stored in the
separate `agent-workflow-coordinator-state` repository, never in the product
authority repository, as a dedicated ref
`refs/handoffctl/barrier/<project_id>` whose commit contains only the strict
barrier record and schema metadata. `handoffctl` owns the repository-common
lock, creates the blob/tree/commit in a temporary object transaction, fsyncs
the object and ref directories, and performs compare-and-swap with
`git update-ref <new> <expected-old>`. The CAS record contains the immutable
identity digest, envelope digest, owner/token/revision, and status. Barrier
acquire/recheck/begin-release/release are the only permitted ref transitions;
stale recovery first CASes `held` to `ambiguous`. The ref and its commit are
the durable selector; no product checkout, generated view, or product Git
working tree is modified. SQLite-mode uses the equivalent dedicated state
backend row and transaction, with the same schema and transitions.

### Private filesystem evidence

Absolute paths, root-relative paths, device numbers, inode numbers, directory
FDs, and temporary names are private journal/backend evidence only. They are
never emitted in public state, manifests, PR text, logs, or error messages.
Public evidence contains only opaque artifact IDs, schema-safe identities, and
cryptographic digests. The implementation must test this redaction boundary.

## BackupBoundary v5 correction (2026-09-14)

The v4 in-repository barrier ref is rejected because Git backup uses
`--all`/`show-ref`; a held or releasing barrier ref would contaminate the
authority artifact and could be restored stale. The control plane is therefore
separate from the authority backup domain.

For Git coordination, `handoffctl` uses a separately provisioned bare control
repository for each project (the control repository is not the product
repository or the state-authority repository). Its barrier ref and commits are
never included in authority bundles, refs, indexes, manifests, authority
revisions, or restore destinations. The control repository has its own lock,
CAS/ref durability, fsync and recovery contract. For SQLite coordination, the
barrier row is in a separately provisioned control database, not the backed-up
authority database, with the same schema and CAS transitions. A deployment
without the configured control store fails closed before quiescence.

The acceptance model must exercise the exact sequence `held -> backup verified
-> released`, then force rollback and prove the control barrier remains
`released` or is explicitly reclaimed through `ambiguous -> held` under a
newer fenced operation; it must never be restored from the authority backup.
Tests must assert authority Git ref/object equivalence excludes the control
store, SQLite restore excludes the control database, and stale held/releasing
control state cannot be silently imported during rollback. Formal mappings and
task evidence must reference the effective v3/v4/v5 contract, not the
superseded in-repository barrier-ref wording.

## BackupBoundary v3 corrections (2026-09-14)

The v2 design is rejected until these lifecycle details are explicit. This
section supersedes conflicting v2 wording and remains design-only.

### External barrier store and lock order

The authoritative barrier is not stored in the product Git worktree and never
publishes a dirty Git checkout. It is a record in the coordination state
backend (SQLite WAL authority, or the equivalent dedicated state-backend
transaction), owned by `handoffctl` rather than by the upgrade engine. Its
strict schema is `{schema_version, barrier_id, project_id, operation_id,
state_revision, authority_revision, fencing_token, fencing_owner, status,
envelope_digest, created_at, updated_at}` with `status` in `held`, `releasing`,
`released`, or `ambiguous`. `handoffctl` exposes one public CAS API for
`acquire`, `recheck`, `begin_release`, `release`, and stale-owner recovery;
callers cannot provide an alternate lock path or mutate the record directly.

The public API acquires the repository-common coordination lock exactly once,
performs the barrier transaction, fsyncs/commits the state backend, and keeps
that lock held through the caller-supplied critical section. The engine must
not reacquire the same lock. The product-authority lock is a distinct,
deterministically ordered lock acquired only after the coordination barrier;
all operations use this same order. Recovery may reclaim only an expired
owner with a strictly newer state revision and must CAS `held` to `ambiguous`
before any cleanup. A missing, stale, or conflicting record fails closed.

### Canonical envelope and path identity

The envelope is serialized as canonical UTF-8 JSON: recursively sorted object
keys, no insignificant whitespace, UTF-8 with no BOM, integers only where the
schema says integer, and no NaN/Infinity or implicit type coercion. Its
`envelope_digest` is SHA-256 of those exact bytes. Paths are normalized to
absolute lexical paths, then represented in evidence by a root-relative
POSIX path plus `(device,inode)` after opening; source identity is captured
before and after backup. Nonexistent outputs are created only with dirfd/
`O_NOFOLLOW`-equivalent operations under the validated root. After every
create, rename, or replacement, the engine reopens by descriptor, checks
device/inode and resolved containment, recomputes the envelope/artifact
digest, and rejects any alias or swap. No path string is emitted publicly.

### Journal, barrier, and reopen crash protocol

`PhaseContext`, every journal record, and every admission snapshot must bind
`project_id`, `operation_id`, `state_revision`, `authority_revision`,
`fencing_token`, `fencing_owner`, `durable_barrier_id`, and
`envelope_digest`; missing or changed values invalidate the operation. The
durable sequence is: acquire/CAS barrier `held` and commit it; fsync journal
`barrier-held`; perform backup and verification; fsync journal `verified`;
CAS barrier to `releasing` and commit; re-read authority and admission; then
CAS barrier to `released` and commit before fsyncing journal `completed`.
The lock is held throughout. A crash is reconciled by this table: `held` with
no verified record resumes or rolls back under the same operation; `verified`
with barrier `held` resumes release/reopen; barrier `releasing` is re-read and
completed only if postconditions hold, otherwise becomes `ambiguous` and
safe mode; barrier `released` with no completed journal is reconciled from
the exact envelope and postconditions, never blindly repeated. No recovery
releases a barrier before validated reopen or silently reopens an ambiguous
operation.

### Implementation gate and evidence

The hostile test matrix is an executable acceptance gate in the implementation
change, not a prerequisite claim of this design document. The implementation
PR must add and pass tests for the schema/CAS transitions, lock order and
contention, canonical digest and path swaps, post-create alias checks, every
crash point in the sequence above, and all backend equivalence/fault cases.
Independent review must map each test and formal obligation to this v3 text;
publication remains blocked until that exact evidence is green.
