# AR-0007: Upgrade engine and rollback

Implement the explicit `upgrade check`, `upgrade plan`, `upgrade apply`, and
`upgrade rollback` flow. Use the repository-common lock, durable phase records,
bounded commands, atomic replacement, exact revisions, and idempotent resume.

The engine must distinguish preflight failure, staged-but-not-committed
failure, post-upgrade failure, rollback failure, and ambiguous external
results. It must never claim success while the runtime, binding, backend,
projections, or backup state is uncertain.

## BackupBoundary v2 normative design (2026-09-14)

This section is a design gate, not an implementation claim. No adapter may be
published until an independent reviewer accepts this contract and its hostile
tests.

### Envelope and path domain

Every operation carries a strict serialized envelope with exactly these
fields: `schema_version=2`, `backend` (`git` or `sqlite`), `project_id`,
`operation_id`, positive `state_revision`, `authority_revision`,
`fencing_token`, `fencing_owner`, `durable_barrier_id`, `artifact_root`,
`source`, `destination`, `manifest`, and `quiescence_record_digest`.
Identity strings use `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; UUID/project values
are validated by their existing project contract. Public evidence exposes
only opaque artifact IDs and digests, never host paths.

`artifact_root` is an existing, non-symlink directory owned by the authority.
Only generated outputs (`destination`, `manifest`, and operation sidecars)
must be beneath its resolved inode; the live source may be the configured
Git/SQLite authority outside that root. Source and every output must be
existing/typed as required by the backend or a non-existing output target,
respectively; no source/output or output/output ancestor/descendant overlap is
allowed. All lexical ancestors and leaves reject symlinks, and resolved inode
identity rejects hard-link aliases. Existing outputs are never overwritten.

### Authoritative barrier and lock sequence

The engine obtains the repository-common `handoffctl.coordinator_lock_path()`
lock first; callers cannot select a substitute. Under that lock it acquires
the authoritative durable barrier using compare-and-swap on
`durable_barrier_id`, records owner/token/state revision, and fsyncs the
barrier record and containing directory. It then re-reads the barrier,
authority revision, project binding, backend selector, and fencing token
immediately before backup and immediately after verification. The barrier is
held through backup, isolated restore-equivalence verification, manifest
publication, and post-check; release is a durable reopen operation after the
engine records success. Any mismatch, stale owner, lost barrier, or failed
re-read fails closed.

### Durable operation/retry state

The operation journal stores the canonical envelope digest, output artifact
digests, phase, and outcome. A retry with absent outputs is allowed only for
the same operation ID and exact envelope when no terminal artifact record was
published; a terminal verified record is idempotently returned without
rewriting outputs. Any partial output, digest mismatch, changed path, stale
revision, or ambiguous external result enters reconciliation/safe mode and
cannot be blindly retried. Recovery must distinguish `started`, `published`,
`verified`, and `ambiguous` records.

### Backend API and durability contract

Adapters use bounded public APIs. Git backup/restore must use bounded commands
with explicit timeout, complete refs/object/index/worktree evidence, and
restore into an operation-unique isolated destination followed by commit,
ref, tree, and binding equivalence checks. SQLite must obtain binding and
authority revision from the live store, use the online backup API, persist a
canonical sidecar manifest, and restore with integrity, WAL, binding, and
projection equivalence checks; caller booleans and supplied binding alone are
not evidence. Every artifact file is written, flushed, fsynced, atomically
renamed, and followed by directory fsync in that order. Rename, fsync,
cleanup, timeout, process death, and directory failure at each boundary
produce an explicit failed/ambiguous outcome; no success is reported after an
uncertain durability point.

### Required review evidence

Before implementation approval, tests must cover source outside root,
ancestor overlap, symlink and hard-link aliases, malformed identities and
stale authority/barrier/fence revisions, common-lock contention and ordering,
same-operation retry/recovery, concurrent different operations, every write/
rename/fsync/cleanup/timeout fault, process death at each durable boundary,
Git/SQLite restore equivalence, and privacy-safe evidence. The design remains
blocked until these predicates are independently reviewed and mapped to the
formal model.
