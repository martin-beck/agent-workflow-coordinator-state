# AR-0012: Durable upgrade barrier and SQLite write fencing

Implement the contract described by GitHub issue [#27](https://github.com/martin-beck/agent-workflow-coordinator/issues/27)
as the first executable successor of AR-0007. The goal is a durable, project-scoped admission
barrier that makes upgrade quiescence real for both the upgrade engine and the SQLite authority.
The coordinator must remain usable on every success, interruption, crash, and failure path; any
uncertainty is a rejection-only safe mode.

Dependencies and boundary:

- AR-0007 supplies the upgrade-engine phase, journal, and rollback contract. Do not enable
  `handoffctl upgrade apply` or `rollback` before this AR is independently reviewed and merged.
- AR-0008 consumes this AR's exact executable seam for formal refinement. Its model must be
  extended and rebound to implementation tests after the barrier/fencing implementation exists;
  this AR must not fabricate a refinement claim before then.
- Keep Git-backed coordination and the existing non-upgrade workflow usable. Do not alter
  generated state views or vendored coordinator files as part of the task record.

Required implementation:

1. Define typed barrier-session and child-operation records with immutable project/session,
   owner, attempt, digest, revision, and fencing-token identity. Enforce only
   `absent -> held -> releasing -> released`; route uncertain or contradictory observations to
   durable `ambiguous` safe mode.
2. Acquire and commit the barrier beneath the single lock order repository-common lock,
   control-store lock, authority lock. Recheck the barrier before admission and before every
   authority transaction. Snapshot and verification callbacks remain side-effect free.
3. Bind forward/new and failure/rollback children to one held session. Record bounded in-flight
   wrapped commands and fsynced result journals; stop new starts, drain in-flight work, and defer
   authoritative result append until verified reopen.
4. Fence every SQLite authority mutation route: task changes, migrations, result appends,
   observations, and mutating reconciliation. Reject held, releasing, ambiguous, stale,
   mismatched, aliased, corrupt, or unprovisioned control state with stable fail-closed errors.
5. Add an atomic compatibility/provisioning marker. Preserve normal operation for an existing
   installation without that marker while rejecting upgrade admission until provisioning is
   independently verified.

Verification and publication gates:

- Public-boundary tests cover ordering, CAS/fence/owner/revision rejection, competing attempts,
  in-flight drain, every SQLite mutation route, control DB and WAL/SHM swaps, lock timeout and
  re-entry, and process death at every durability boundary.
- Run independent-process crash and write-rejection tests after upgrader termination. Demonstrate
  that writes resume only after an independently verified `released` state and that both old and
  new runtimes remain usable at externally observable boundaries.
- Extend the storage/upgrade TLA+ model and bind each invariant to exact implementation tests.
  Record model/config/tool hashes, bounded coverage, and explicit non-claims.
- Require focused and full tests, quality gates, signed DCO checkpoint, independent exact-head
  review, green CI, and post-merge verification before releasing AR-0012.

Failure policy:

No best-effort recovery or manual journal repair is permitted. If lock ownership, durable state,
control-store identity, fencing token, WAL/SHM identity, child result, or reopen verification is
ambiguous, reject all mutation, preserve evidence, and require an independently verified
reconciliation path. Rollback must remain under the same barrier and must itself be proven before
any release transition.
