# AR-0031: Executable upgrade mutation and rollback boundary

Implement the first production-safe mutation slice needed by the correctness-first
upgrade path. The existing Git and SQLite authority adapters intentionally fail
closed for mutation; this AR must make one bounded phase executable without
weakening admission, fencing, backup, selector, or rollback guarantees.

## Required boundaries

- preserve the current fail-closed behavior for unsupported phases;
- implement one explicitly scoped backup/commit/rollback path only after a
  validated barrier, lease, authority identity, and generated operation record;
- prove that every injected failure leaves either the verified old runtime or
  the verified new runtime selected and functional;
- cover Git and SQLite behavior separately where their authority semantics differ;
- add contract, hostile, process-death, and formal correspondence evidence before
  enabling any additional mutation phase;
- require independent review, exact-head hosted gates, post-merge Verify, and
  durable state reconciliation.

The AR does not authorize broad mutation enablement or dispatch of unimplemented
phases. Unsupported operations must continue to fail closed.

## Authority-neutral durable binding design (pre-implementation)

The missing Git seam must be added as a shared contract, not by making Git
pretend to be a SQLite authority. A future executor should depend on these
interfaces:

```text
DurableAuthorityBinding
  authority_kind: git | sqlite
  authority_identity(): immutable descriptor/inode or repository identity
  reread_identity(): same identity or AmbiguousState
  operation_lock(): common -> control -> authority lock order

DurableUpgradeSession
  capture(): {project, operation, state_revision, authority_revision,
              barrier_id, fencing_owner, fencing_token, identity_digest}
  assert_current(snapshot): reject stale, replaced, ambiguous, or released state
  journal_snapshot(): immutable journal identity/content snapshot
  record_outcome(operation_id, opcode, result): atomic durable append + fsync
```

The binding is constructed only by a trusted factory after validating the
control-store authority kind/path, barrier status (`held` only), CAS revision,
fencing token/owner, operation identity, and authority identity. Callers may
not supply a mutable callback or a path-only identity. Every backup operation
must capture the session and authority snapshots before the effect, hold the
ordered lock across the effect, reread both after the effect, and record the
outcome atomically. Any uncertain close, fsync, process death, identity swap,
or journal replacement enters `ambiguous` safe mode.

Migration compatibility is read-only: existing SQLite v10 barrier records are
accepted only when their authority-kind binding is explicit; legacy records and
Git installations without the new binding marker may observe state but cannot
execute an operation. No migration may silently infer Git identity from a
pathname or convert an old record into an executable session.

Required evidence before implementation can be enabled:

- hostile authority/control/journal replacement and ancestor symlink swaps;
- stale revision, foreign project, forged operation, replay, fencing-owner, and
  barrier-status rejection;
- process death before effect, during effect, after effect before journal fsync,
  and after journal fsync, with deterministic recovery classification;
- Git clean-tree/ref identity and SQLite database/WAL/SHM identity checks;
- concurrent reader continuity proving no absent or partially authoritative
  state;
- contract tests for the exact generated opcode and durable outcome schema;
- bounded formal correspondence for the implemented transitions only.

Until this design has an independently reviewed implementation and evidence,
Git generated dispatch and all replace/commit/rollback paths remain disabled.
