# AR-0031: Executable upgrade mutation and rollback boundary

Implement the first production-safe mutation slice needed by the correctness-first
upgrade path. The existing Git and SQLite authority adapters intentionally fail
closed for mutation; this AR must make one bounded phase executable without
weakening admission, fencing, backup, selector, or rollback guarantees.

## Required boundaries

- preserve the current fail-closed behavior for unsupported phases;
- implement one explicitly scoped backup/commit/rollback path only after a
  validated barrier, lease, authority identity, and generated operation record;
- prove that every injected failure leaves either the verified old runtime or
  the verified new runtime selected and functional;
- cover Git and SQLite behavior separately where their authority semantics differ;
- add contract, hostile, process-death, and formal correspondence evidence before
  enabling any additional mutation phase;
- require independent review, exact-head hosted gates, post-merge Verify, and
  durable state reconciliation.

The AR does not authorize broad mutation enablement or dispatch of unimplemented
phases. Unsupported operations must continue to fail closed.

## Pre-implementation design: durable authority-neutral binding

Before Git generated operations can be enabled, introduce a shared binding
contract rather than adapting the SQLite-specific store by assertion:

- `DurableAuthorityBinding` identifies the backend, project, authority identity,
  control-store identity, and journal identity. Git identity is a validated
  repository descriptor (device/inode, resolved project root, branch, and exact
  head); SQLite identity remains the existing regular-file descriptor contract.
- `DurableUpgradeSession` is created only by a trusted factory after validating
  selector reference, expected revision, barrier id, fencing token, lease,
  authority identity, control-store identity, and journal identity. The factory
  rejects missing, substituted, symlinked, or backend-mismatched paths.
- Every effect follows one ordered protocol: acquire the durable barrier and
  operation lock; reread all identities and the journal; verify the generated
  operation and fencing context; perform one bounded backend effect; fsync the
  effect and its durable outcome; reread identities and journal; release only
  after the postcondition is proven. Any failed or ambiguous close/fsync/reread
  enters safe mode and never guesses whether the effect committed.
- Legacy SQLite sessions remain compatible through an adapter over the existing
  `SQLiteBarrierSessionStore`; legacy Git installations without the new durable
  binding remain fail-closed. No migration may silently infer a Git control
  store or fencing token.
- Required evidence before dispatch: contract/schema tests; hostile replacement,
  symlink, replay, stale-revision, fencing, and lock-order tests; process-death
  tests at each effect/fsync/journal boundary; concurrent-reader continuity;
  exact old/new runtime selection checks; and bounded formal correspondence for
  the session state machine. Only after these pass may a Git `backend.backup`
  executor be considered for an independently reviewed slice.

The design deliberately does not enable Git dispatch, selector mutation,
replace/commit, rollback, or broad `UpgradeEngine.apply`. Those remain
fail-closed until the contract and its evidence are implemented and merged.
