# AR-0032 plan: multi-revision durable session identity contract

## Safety boundary

This is an additive contract and verification slice. It does not enable upgrade mutation, release publication, or worker dispatch. Until AR-0031 independently passes its gates, the coordinator remains fail-closed and any uncertain durable write remains permanently ambiguous.

## Decisions fixed for this slice

- `session_id` is generated by the trusted authority/session factory and is never caller supplied.
- `session_id` identifies one logical session; `journal_identity` identifies the physical journal generation. They are intentionally distinct.
- `journal_sequence` is strictly contiguous and monotonic within a session. Gaps and regressions are rejected.
- `operation_id` is unique for every forward or rollback operation. Rollback additionally records `parent_operation_id`.
- `previous_record_digest` is a canonical hash-chain link. The first record uses an explicit genesis/null value; every later record must link to the exact prior record.
- The authority/barrier/fencing tuple remains immutable for a session: `authority_identity`, `barrier_id`, `fencing_owner`, and `fencing_token`.
- `state_revision` remains the per-record authority/CAS revision and must advance according to the existing transition rules.
- Exact byte-identical replay is accepted idempotently. Any conflicting duplicate, replacement identity, tamper, stale revision, or uncertain append/fsync is rejected and contained in ambiguous-safe mode.

## Implementation slices

1. Add canonical schema/types and deterministic serialization for `session_id`, `operation_id`, `parent_operation_id`, `journal_sequence`, `previous_record_digest`, `state_revision`, `journal_identity`, authority identity, barrier and fencing fields, status, and fsync state.
2. Add a validator/reconciler that distinguishes exact replay from all conflict classes and never silently repairs a chain.
3. Add read-only compatibility handling for legacy records; legacy data may be inspected but cannot authorize a new mutation or dispatch.
4. Add hostile/process-death tests at append, fsync, replay, and terminal reread boundaries.
5. Extend the bounded TLC model and refinement mapping with append, replay, reject-conflict, and crash-after-append-before-fsync actions and the invariants listed in the task.
6. Run focused tests, fast formal, AWQ/scope, and trusted post-merge checks. Reconcile the state repository only after exact-head evidence is recorded.

## Explicit rejection matrix

Reject sequence gaps/regressions; changed session, operation parent, journal generation, authority, barrier, owner, or fencing token; changed bytes for an existing sequence; broken previous digest; stale state revision; terminal reread that is not byte-identical; and any uncertain fsync/process-death outcome. Never infer a safe continuation from absence of evidence.

## Handoff to AR-0031

When this AR is complete, update AR-0031 with the exact contract revision and evidence. AR-0031 must then implement the first bounded mutation slice and retain mutation/dispatch disabled until its own formal, hostile-runtime, and post-merge gates pass.
