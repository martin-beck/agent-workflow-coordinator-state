# AR-0055 plan: legacy umbrella reconciliation and correctness-first repair

## Safety invariants (apply to every phase)

1. The coordinator remains usable for ordinary coordination throughout. Upgrade
   code may reject, quarantine, or enter an explicitly documented ambiguous
   state, but may never leave a partially selected runtime or partially
   authoritative state.
2. No selector publication, runtime replacement, commit, apply, rollback, or
   release publication is enabled merely because a test fixture passed. Each
   operation requires an exact-head implementation, an independently reviewed
   contract, hostile/process-death evidence, green hosted gates, and post-merge
   verification.
3. Any uncertainty (identity, ownership, revision, fsync, lock state, child
   result, WAL/SHM, journal, or reopen) is rejection-only and durable. Recovery
   must preserve evidence and require an independently verified reconciliation.
4. The stable bootstrap and the last known-good runtime remain available until
   the new runtime has been independently validated and atomically selected.
5. Every claim is bounded to the exact model, implementation head, tests, and
   environment that produced it; no Python/TLA+ refinement or live-upgrade
   claim is inferred from read-only evidence.

## Phase 0 — authoritative gap audit (AR-0055)

1. For AR-0009, AR-0012, AR-0013, and AR-0031, extract the objective,
   dependencies, acceptance criteria, latest state revision, and linked GitHub
   issues/PRs.
2. Build a requirement matrix with one row per obligation and classify it as
   **proven**, **superseded with explicit successor**, **blocked**, or
   **missing**. Attach exact merge SHAs, check-run IDs, test commands, and
   non-claims; do not close an AR from indirect child evidence.
3. Reconcile the matrix with GitHub and state, then run `doctor --live`. Any
   stale generated state, unreachable PR, or contradictory lease is repaired
   before further implementation.

## Phase 1 — formal contract and model binding (successor AR)

1. Extend the v10 refinement contract for the exact implementation seams that
   will be enabled: barrier/CAS transitions, ordered locks, authority identity,
   selector visibility, retained-descriptor execution, journal durability,
   crash classification, and recovery.
2. For each transition, define preconditions, postconditions, invariants,
   forbidden states, and a correspondence map to named implementation tests.
3. Run bounded fast TLC on every PR/commit; run the exhaustive model weekly
   with the multi-hour timeout. Publish model/config/tool hashes and explicit
   state-space limits. The mutation gate remains deny while any required
   correspondence is not proven.

## Phase 2 — durable barrier and fencing (successor of AR-0012)

1. Construct barrier sessions only through a trusted factory; bind project,
   operation, owner, fencing token, revision, authority identity, and digest.
2. Enforce `absent -> held -> releasing -> released`; route stale, aliased,
   corrupt, contradictory, or process-dead observations to durable
   `ambiguous` safe mode.
3. Enforce repository-common -> control-store -> authority lock order and
   reread the barrier before every transaction and after every effect.
4. Fence every SQLite mutation route and cover database/WAL/SHM replacement,
   lock timeout/re-entry, competing owners, stale CAS, and process death.
5. Demonstrate ordinary reads/coordination remain available and writes resume
   only after independently verified `released`.

## Phase 3 — selector and versioned runtime (successor of AR-0013)

1. Keep the bootstrap immutable; stage complete versioned runtimes offline.
2. Validate bounded selector syntax, ownership/modes, allowlisted path,
   manifest, exact commit/tag identity, signature/trust policy, and permanent
   project binding.
3. Use descriptor-bound/no-follow reads (read-until-EOF) and atomic selector
   publication with directory fsync and explicit ambiguous-fsync recovery.
4. Test symlink, hard-link, ancestor, pathname replacement, partial staging,
   selector races, malformed/oversized input, and validation-to-exec swaps in
   independent subprocesses.
5. Dispatch only the retained, validated descriptor; otherwise continue the
   known-good runtime or reject without dispatch.

## Phase 4 — bounded mutation slices (successor of AR-0031)

1. Implement one operation at a time, starting with backup and durable outcome
   recording; leave unsupported phases rejection-only.
2. For Git and SQLite separately, capture identity/session before the effect,
   hold the ordered lock across it, reread after it, fsync the outcome, and
   classify every uncertain boundary as ambiguous.
3. Add failure injection at before/during/after effect, journal fsync, process
   death, reopen, and recovery. Prove either the verified old runtime or the
   verified new runtime remains functional at every externally visible point.
4. Promote selector publication, runtime replacement, commit, apply, and
   rollback only in separate reviewed ARs, each depending on the prior gate.

## Phase 5 — first release integration (successor of AR-0009)

1. Generate release-specific preconditions and postconditions from the proven
   contract; validate fresh-clone state, exact release identity, artifact
   ownership/digests, and compatibility markers.
2. Execute isolated upgrade campaigns for every phase and injected failure,
   including rollback while the same barrier remains held. Verify the old or
   new runtime is functional before reopening writes.
3. Keep publication unsigned as currently permitted by policy, but require an immutable
   tag, exact source binding, reproducible artifacts, privacy-safe evidence,
   independent review, hosted gates, post-merge verification, and live doctor.

## Publication and stop rules

- A successor AR is complete only after exact-head review, fast formal, focused
  and full tests, hosted CI, post-merge Verify/Formal, state reconciliation,
  and `doctor --live` all agree.
- If any check times out, is skipped, loses its worker, or has stale evidence,
  classify the result as unknown and do not enable the next mutation.
- Close or supersede legacy ARs only after the matrix names the successor and
  preserves all unmet obligations; never convert read-only evidence into a
  live-upgrade claim.
